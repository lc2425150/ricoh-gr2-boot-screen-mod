理光 GR II 固件可行性分析

针对开源项目 radium-wang/ricoh-gr4-firmware-analysis-and-feature-expansion 对 GR II 的适用性 · 基于官方固件 rg2_v003 的离线实测 · 2026-10-03

结论：仓库的工具与流程不能直接用于 GR II，但其底层机制与 GR II 同源。

GR II 固件是可解密的（公开工具 + 静态密钥），且固件内部确实存在与 GR III/IV 同一套 TTL 脚本解释器， 含 filecopy / filesearch / execcmnd 等命令以及 Startup.ttl / Shutdown.ttl 加载路径。 但该仓库赖以工作的入口机制在 GR II 固件中不存在同名实现——没有 DEVELOP.MOD、没有 OPEN_FACTORY_DEBUG_MENU、 没有 GR IV 的关机图资源名。因此现状是：前置条件具备，触发路径未知。

第二轮（固件层逆向）新增结论 —— 结论已向上修正：

  • 架构确认：载荷为 ARM 大端（BE-32）+ Thumb-2；b01firm8.bin 装载基址 0xa0020200 + 文件内偏移（等价于 0xa0020400 + 加载表偏移，二者相差文件头 0x200）。
  • 资源层已完全掌握：b01firm6.bin 是机内 A: 盘的完整文件镜像， 121 个条目（名称 / 偏移 / 大小）全部解出，可直接定位与替换。
  • 脚本能力已被证实：镜像内含理光出厂 TTL 脚本 A:/update.ttl， 且脚本通过 syscom get/set <index> <value> 读写系统配置 —— 与 GR IV 工厂脚本接口同一设计思路。
  • 触发门控已定位到函数与字段：*:/Startup.ttl 由 job 0 的启动阶段处理函数（0xa00e879a）加载，其上游存在由 ctx+0x68 / +0x78 / +0x7c 三个字段构成的合取门控。

缺口从"机制是否存在"缩小为"哪条用户动作置位这三个上下文字段"。详见第 7 章。

第三轮（作业调度与控制台）新增结论 —— 这是本轮最重要的发现：

  • 整机作业调度表已被完整解出：105 条 JOBID_* 条目（表索引 = 作业号）， 覆盖开机 / 关机 / 拍摄 / 播放 / 固件升级全部状态机。
  • Startup.ttl 与 Shutdown.ttl 的归属已确认：前者在 job 0 的启动阶段函数内，后者在 JOBID_SHUTDOWN（作业 9）函数内——两者都是相机自身开/关机流程的一环。
  • 固件内含两套"工厂界面"：一套产线测试控制台（1–10 项测试 + all / set / show）， 一套宿主端调试 shell（comp / read / write / GPIO 控制，传输可选 uart 或 ptp）。
  • 固件升级链路已还原：Install Files → Run Update Script(E:/A:/H:/update.ttl) → fsys stop → fe -e → fsys start → up -noreboot， 并有独立作业 JOBID_CHECK_FW_FILE / JOBID_FW_UPDATE。

意义：GR II 缺少的不是"脚本能力"，而是 GR IV 那种卡内触发文件； 它走的是控制台 / shell 通道。详见第 8 章。

2.3 加密方案：512 字节块 · 单字 XOR · 步进密钥

先于工具只见高熵数据，实测发现三条互相印证的线索，随后与公开实现完全吻合：

  • 全文件字节分布近乎完美均匀（熵 7.9998 bits/byte，256 个取值均匀分布）——但 deflate 仍能压缩 38%。
  • 存在 5311 段、长度恒为 512 的 4 字节周期结构，其中 3207 段严格落在 offset % 512 == 0 栅格上，且每段对应一个互不相同的 4 字节单元。
  • 这两点只能由「每 512 字节整块被一个 32 位字异或」解释：明文中的常量填充区（如全 0xFF）在密文中变成该块唯一密钥的周期重复， 于是既拉高了字节熵，又给 LZ77 提供了长匹配。

公开解码器 jokob/ricohdec 的实现与上述推断一致：块密钥自 0xF8E69612 起， 每块递增 0xBE39B193，逐 32 位字异或。解码后熵降至 6.0956（b01firm6）/ 6.4524（b01firm8）， 可读字符串从 2.6% 升至 10.4%，模块名 R_RG2_REFLECTOR 可直接读出。

3 · 复现步骤

1
取得官方固件（自行从理光官网下载，需遵守其条款，本项目不代为分发）： 
curl -L -o rg2_v003.zip \
  https://www.ricoh-imaging.co.jp/english/support/digital/firmware/rg2_v003.zip
unzip rg2_v003.zip        # → rg2_v003/rg2_v003.frm (14,033,920 B)
2
编译并使用公开解码器（jokob/ricohdec，约 120 行 C）： 
cc -o ricohdec ricohdec.c
./ricohdec rg2_v003.frm     # → b01firm6.bin + rg2_v001up.bin
./ricohdec rg2_v001up.bin   # → b01firm8.bin
本次实测输出：dircount=2 → flen=7896704 b01firm6.bin mode=encrypted、 flen=6134784 rg2_v001up.bin mode=container → flen=6132308 b01firm8.bin mode=encrypted。
3
在明文上做接口检索（本次使用的脚本位于 gr2-analysis/out/）： 
strings -a -n 5 b01firm8.bin | grep -E "filecopy|Startup|Shutdown|Shell"

全过程为纯离线只读：未连接相机、未写入任何介质、未生成任何可安装固件。

5 · 风险与边界

  • 不要照搬仓库流程。把 GR IV 的 00078560.636 / DEVELOP.MOD 放进 GR II 的 SD 卡没有意义； 目标路径与入口都是固件特定的，误写机内资源存在风险。
  • 本报告未做任何设备侧验证。全部结论来自离线静态分析，不等于 GR II 上可以真正加载并执行 Startup 脚本。 「固件里存在 TTL 解释器」与「能够在 GR II 上触发它」是两件事。
  • 版本与样本绑定。本次结论仅对应 rg2_v003（2016-06-28 构建）。其他版本需重新核验哈希与偏移。
  • 法律与授权。固件版权属理光，下载与使用受其条款约束；该仓库自身采用非商业源码许可（非 OSI 开源），商用需另行取得书面许可。

6 · 未解决问题与建议路径

  1. 核心缺口：如何触发 Startup.ttl。 需要逆向 GR II 的脚本加载状态机——即哪个持久化标志位、经由哪条菜单或按键路径被置位。 这是唯一决定「能否落地」的问题。
  2. 次生缺口：是否存在进入工厂/调试菜单的入口。 GR II 明文中存在 camera mode : %02x 与 A:/fix/ 出厂文件组， 提示有对应机制，但入口方式未定位。
  3. 可低成本推进的方向：以 b01firm8.bin 的加载地址表为锚点做重定位分析， 定位脚本加载函数与 Startup.ttl 字符串的交叉引用。
  4. 若目标是尽快出成果，建议改在 GR IV 或 GR IIIx Urban 上按仓库流程操作——路径已验证， 而 GR II 属于「需要先完成一轮独立逆向」的课题。

7 · 第二轮：固件层逆向结果

7.1 架构与地址空间

载荷为 ARM 大端指令集（BE-32），代码区混用 ARM 与 Thumb-2。三项独立验证：

  • 头部的版本、日期、长度字段均为大端序（构建日期 0x20160628、时间 0x00190639）， 与容器目录条目一致，也与理光/宾得固件的大端传统吻合。
  • 偏移 0x400 处为标准 ARM 异常模式初始化序列：连续 5 组 msr cpsr_c, #0xd3/#0xdb/#0xd7/#0xd1/#0xd2 紧跟 ldr sp, [pc, …]，覆盖 SVC / UND / ABT / FIQ / IRQ 五个模式。
  • Thumb-2 解码在 0xc9000 起连续覆盖 512/512 字节且出现函数序言 push {r0,r1,r2,r4,r5,r6,r7,lr}，排除误判为数据的可能。

b01firm8.bin 的加载表为 5 字一组的大端记录 (file_offset, dest1, size1, dest2, size2)， 数据按 1024 字节对齐。前 16 组有效条目全部满足同一条映射：

runtime address = 0xa0020400 + 加载表偏移          # 16/16 组吻合
runtime address = 0xa0020200 + 文件内偏移          # 等价写法

交叉验证例：第 1 组 表偏移 0x0 → 0xa0020400；第 2 组 表偏移 0xa4800 → 0xa00c4c00 ；第 3 组 表偏移 0x10bc00 → 0xa012c000。三组均满足 dest1 − 表偏移 = 0xa0020400。

地址基准修正（第三轮）

上一轮把两种偏移混用，导致所有由文件内容反推的运行时地址整体高出 0x200。 加载表的 file_offset 字段是从文件头 0x200 之后起算的，而按搜索结果定位字符串 / 代码得到的是真实文件偏移。 两者相差一个 512 字节头。现已用两条互相独立的证据钉死：

  • 字符串 "JOBID_BOOT" 位于真实文件偏移 0x0F5580，而作业调度表存的指针是 0xa0115780 = 0xa0020200 + 0x0F5580。
  • shell 命令串 "set res uart (CH) (BAUD) (TXRES) (RXRES)" 位于真实文件偏移 0x0A19FB， 其参数表项指针 0xa00c1e09 与 0xa0020200 + 0x0A1C09 一致。

本报告第 7 章中由内容反推的地址已按新基准修正（旧值 +0x200 即为旧记录）； 第 8 章全部采用修正后基址。

7.3 出厂 TTL 脚本与 syscom 配置接口

A:/update.ttl（4,598 字节）是理光随固件出厂的脚本，头注为 @date 12SEP12 Y.Watanabe(RICOH)、Copyright(C) 2011-2015 by RICOH COMPANY, LTD.。 正文可读，节选：

:Main
    call updateCom
    call dispVer
    call deleFixFile
    end

:updateCom
    sprintf "syscom reload"
    sendln inputstr
    sprintf "syscom get 0 "
    sendln inputstr
    if result != UPDATE_VER then          ; 版本不符
        sprintf "syscom set 0 0x%x" UPDATE_VER
        sendln inputstr
        sprintf "syscom get 1 "                ; brlEnable(保持)
        sendln inputstr
        ...
        sprintf "syscom set 2 0x06E"           ; tmpErr
        sendln inputstr
        sprintf "syscom set 3 594"             ; volErrLow

三点意义：

  • 脚本可使用 Tera Term 的 sprintf / sendln / inputstr / call / end 与控制流语法，即 GR IV 那套 TTL 解释器在 GR II 上真的会被执行（这是出厂脚本，不是死代码）。
  • 存在结构化的系统配置接口 syscom get / set <index> <value>， 索引 0=版本、1=brlEnable、2=tmpErr、3=volErrLow。
  • 脚本带版本常量 UPDATE_VER = $00000115，说明这套脚本机制自 2011 年起跨机型沿用。

7.4 Startup.ttl 的门控代码

*:/Startup.ttl（运行时地址 0xa00e934b）与 *:、script %s、 H:/RADJ/%s/Adjust.ttl 同处一个函数内联字面量池（该池同时含指针 0xa00e84af、0xa012a0f4、0xa06c1cf4、0xa012a0ec 与常量 0x25e、0x257、0x2d7、0x23b）。

其上游存在一条门控序列，反复调用访问器 0xa00e5f20 取得上下文指针后逐个检查字段：

0xa00e9234: bl  0xa00e5f20            ; 取上下文 ctx
0xa00e9238: ldr r0, [r0, #0x68]
0xa00e923a: cmp r0, #0
0xa00e923c: beq 0xa00e92a6            ; ctx+0x68 == 0 -> 跳过
0xa00e9242: ldr r0, [r0, #0x78]
0xa00e9246: beq 0xa00e92a6            ; ctx+0x78 == 0 -> 跳过
0xa00e924c: ldr r0, [r0, #0x7c]
0xa00e9250: beq 0xa00e92a6            ; ctx+0x7c == 0 -> 跳过

三个 beq 的目标完全相同，说明这是纯粹的合取条件（AND）：四个条件全非零才继续执行。 门控之前还有一道 ldr r0,[r4,#4] / bne 跳过，即共 四个条件。

上下文指针本身来自字面量池中的常量 0xa06bddf4，该值在整份 b01firm8.bin 中 仅出现一次（就在访问器的池里），说明它由访问器统一发放、不会在各处重复硬编码。 第 8 章定位到该访问器与门控所在函数的身份。

  3. A:/command.txt（37,125 字节）内容非文本，疑为编译或编码产物，未解码。
  4. 条目结构中的 12 字节 ident 字段各条目近乎相同，语义未定。
  5. 本轮所有结论仍为静态分析，相机侧零验证。

8.2 Startup.ttl 与 Shutdown.ttl 的真实归属

用函数序言（push {…, lr}）界定边界后，两条脚本的归属非常明确：

脚本字符串所在函数起始对应作业结论
W*:/Startup.ttl 0xa00e879a 条目 0「refresh」 开机流程的阶段处理函数
*:/Shutdown.ttl 0xa00e98b8 条目 9 JOBID_SHUTDOWN 关机流程的处理函数

job 0 的入口序言为：

0xa00e879a: push {r4, r5, r6, r7, lr}
0xa00e879c: movs r4, r0
0xa00e879e: cmp  r0, #0x10          ; 参数必须 < 16
0xa00e87a0: sub  sp, #0x6c
0xa00e87a2: blt  0xa00e87b4          ; 否则触发断言（行号 0x50）
0xa00e87b4: bl   0xa00e5f20          ; 取表基址
0xa00e87b8: lsls r4, r4, #2          ; index * 4
0xa00e87ba: adds r0, r0, r4
0xa00e87bc: ldr  r0, [r0, #0x14]     ; 表[index].field

关键推论：cmp r0,#0x10 把入口参数限制在 0–15， 配合第 7 章解出的 boot.step / boot.isActivated[SECT_CORE … SECT_END] / boot.sequenceID 属性族，可以判断 job 0 就是开机阶段推进器： 它以阶段号被反复调用，在某一阶段（三个 ctx 标志均置位时）拉起 W*:/Startup.ttl。

因此 ctx+0x68 / +0x78 / +0x7c 不是"用户开关"，而更可能是 开机阶段计数 / 子系统就绪标志。这一结论把第一轮"卡内触发文件"的猜想基本排除： GR II 的 Startup.ttl 是相机自身开机流程的一部分，而不是等待某个外部文件出现。

固件内含一套产线（QC）测试控制台，命令为纯文本菜单（原文含理光自己的拼写错误 upadte）：

意义有三点：

8.5 固件升级链路

升级流程的字符串（与日志文案混排）可直接拼出完整时序：

Install Files
   -> OK (%d files)          / -> error!
Run Update Script.           ; E:/update.ttl  A:/update.ttl
   -> cannot load.
Run Update Script (optional). ; H:/update.ttl
Format LOG drive
fsys stop
fe -e
fsys start
up -noreboot
power-off....
 %s Version : %02X.%02X.%02X

三点结论：

  • 升级会按顺序尝试三个 update.ttl（E: → A: → H:），其中 H: 是可选路径。
  • 脚本执行发生在 fsys stop 之前的可写状态下，说明 update.ttl 具备对内部文件系统动手的能力——这正是 GR IV 工厂脚本的等价物。
  • 三个候选盘符都不是 SD 卡（见 8.6），因此无法直接放一个自制 update.ttl 到卡上触发。

8.9 本轮结论

  1. GR II 与 GR IV 的差异不在"能力"，而在"入口"。 GR II 有完整的 TTL 脚本引擎、有工厂控制台、有调试 shell、有固件升级链； GR IV 仓库的价值恰恰是找到了卡内触发文件这一无需专用工具的通路， 而这在 GR II 上不存在。
  2. 仓库代码依旧无法直接用于 GR II：inspect_firmware.py 的容器解析、 gr4_model.py 的机型 ID（0x132E0/0x132E1/0x13330）、 create_factory_entry.py 的 DEVELOP.MOD 系列文件名，在 GR II 上均无对应物。 结论与第一轮一致，但依据已从"特征缺失"升级为"双向机制对照"。
  3. 若要在 GR II 上出成果，方向应转向控制台 / shell 通道： 即定位 set res shell <uart/ptp> 的进入条件 （按键组合、UART 引脚电平、或 PTP 私有命令）。这需要实机配合， 纯静态分析已接近极限。
  4. 风险提示：产线控制台的 9 inn drive format test、 2 flash erase test、-1 power off 均为不可逆或破坏性操作。 在没有实机与恢复手段前，不建议继续深入触发实验。
