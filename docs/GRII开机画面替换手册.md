> 结论：**可行**。GR II 的开机启动画面是**未压缩的原始帧缓冲**，等长像素级替换即可，

## 〇、先读这一节：路径 A 并不比路径 B 安全

> ⚠ **重要更正**：本文早期版本称「路径 A 更安全 / 路径 B 仅理论可行」，这个表述**不准确**。
> 恰恰相反，在**已知的证据下路径 A 的风险更高**。理由如下。

### 两条路径的真实风险对比

| 维度 | 路径 A · 刷自定义固件 | 路径 B · TTL 脚本覆盖单文件 |
|---|---|---|
| 改动范围 | 整个 `.frm`（14 MB） | 单个 `.brp`（614 KB） |
| **失败后果** | **可能完全变砖，相机无法启动** | 画面异常，相机仍能用 |
| 回滚难度 | 需重新刷原版固件 | 再覆盖回原文件即可 |
| 前置条件 | 无（纯文件操作） | **需先破解机内触发入口（未解决）** |
| 当前可执行性 | 可执行，但**未验证校验和** | 不可执行 |

### 为什么路径 A 风险更高

**决定性证据**：在 `b01firm8.bin`（主程序）里定位到一整套**固件更新包校验字段**：

```
====== %s HEADER ======
nUpdateTotalSize     = %08X
nUpdateFileSize      = %08X
nUpdateCsum          = %08X      <-- 更新包校验和
bExecVerify          = %s        <-- 是否执行校验
bCheckHeader         = %s
bCompareCsum         = %s        <-- 是否比对校验和
bCheckRomSize        = %s
% s is Broken.
```

这意味着相机在刷入固件时会**解析更新头并比对校验和**。而开机画面位于 `.frm` 的
`0x13A400 .. 0x1D0400`（占 4.38%），**几乎必然落在校验范围内**。

**我方工具链目前没有重算这个校验和**——`gr2boot.py frm` 只是把改动的载荷重新加密后
写回原位，其余字节原样保留。所以产出的自定义固件**有较大概率被相机拒绝**，
最坏情况是变砖。

> **关于上一轮的往返验证**：frm 往返 sha256 与原厂一致，只证明「**未改动时**能完美还原」，
> **不能**证明「**改动后**校验和依然正确」。这是个逻辑缺口，我上一轮没有说清楚。

### 关于 `signature` 的排查结论（好消息）

f8 里有 27 处 `signature`，初看像签名校验。逐一核对后确认**全部是内核对象的 magic number**：

```
trace->signature   == SIGNATURE_TRACE
pool->signature    == SIGNATURE_MEMPOOL
task->signature    == SIGNATURE_TASK
semaphore->signature == SIGNATURE_SEMAPHORE
file->signature    == SIGNATURE_FILE
```

这是 RTOS 内核用来发现「对象被踩坏」的断言，**不是密码学签名**。
f6 里确实存在完整的 SHA-256 K 表（64 个常量 @ `0x780F6C`）和 AES S-box（256 B @ `0x77FCF4`），
但**没有任何字面量引用它们**，且 f8 里搜不到 SHA/AES/MD5/CRC 的调用者——
这些是**链接进来的库，运行时未被调用**（可能供将来的加密功能用，或走 HAL/IPSEC 通路）。

**结论：不存在密码学签名校验，挡路的是非密码学的 `nUpdateCsum`。**

### 因此，安全的做法

1. **先解析更新头**——把 `b01firm8.bin` 开头 `0x20` 之后的加载表区与更新头结构对齐，
   定位 `nUpdateCsum` 在 `.frm` 中的确切偏移；
2. **用「只改一个字节」的探针法反推校验算法**——改已知位置 → 观察哪个字段变化 → 反推覆盖范围与算法；
3. **在改画面之前，先用原版固件验证「刷回原固件」这条路确实能开机**，
   确认回滚能力后再动画面；
4. 只有在 1–3 都成立后，才执行画面替换。

**这三条未完成前，不建议刷入任何自定义固件。**

## 一、原理

### 1. 画面在哪

| 项目 | 值 |
|---|---|
| 资源路径 | `A:/img/dvf_TDSt.brp` |
| 所在镜像 | `b01firm6.bin`（机内 A: 盘完整镜像） |
| 镜像内偏移 | `0x00139C00` |
| 目录表条目 | 第 4 条（共 121 条） |
| 文件大小 | **614,400 字节** |

### 2. 格式（实测确定，非推测）

```
640 × 480 像素 × 2 字节/像素 = 614,400 字节     ← 与文件大小精确相等
像素格式：RGB565，大端（big-endian，ARM 原生字节序）
压缩：    无。原始帧缓冲，逐像素平铺
```

**自证方式**：三个 `.brp` 资源大小都恰好等于 `640×480×2`；把文件头按大端 16 位读出来
就是 `e23f`、`e24f`、`d24f` 这类典型 RGB565 像素值；按 RGB565 大端渲染后**直接得到
可读的开机画面**（蓝底白字 RICOH 标志，见下图）。

### 3. 同批资源（可一并替换）

| 资源 | 大小 | 内容（已解码确认） |
|---|---|---|
| `dvf_TDSt.brp` | 614,400 | **开机启动画面**（蓝底 + RICOH 白字） |
| `dvf_key.brp` | 614,400 | 机身线稿图（相机外形） |
| `dvf_mark.brp` | 614,400 | 背面铭牌 / 认证标签（TRA 注册号、FCC、CE、RoHS） |
| `dvf_PBWB.brp` | 53,792 | 尺寸不同，格式待确认 |

> ⚠ **法规提示**：`dvf_mark.brp` 是认证标签，改动它涉及 FCC/CE/IC 等合规标识，
> 自行改装后设备将不再符合原认证声明，请勿用于商业或公开用途。

### 4. 与 GR IV 项目的关系

GR IV 仓库换图靠替换 `A:\Resource\Jpeg\GoodBye.jpg`（JPEG 资源 + `DEVELOP.MOD` 触发）。
GR II 的等价物就是上表这些 `.brp`——**思路一致（换资源文件），载体不同（原始帧缓冲而非 JPEG）**。

GR II 侧**没有** `DEVELOP.MOD`，但这不影响：换画面只需覆盖资源文件本身，
不依赖 GR IV 那套"卡内触发文件"机制。

## 二、工具

`gr2-analysis/out/gr2boot.py`，四个子命令：

```bash
cd gr2-analysis/out
P=/Users/achen/.workbuddy/binaries/python/envs/default/bin/python

$P gr2boot.py info                          # 查看资源信息
$P gr2boot.py extract                       # 解出 brp + 渲染 PNG
#   编辑 bootimg/dvf_TDSt.png（保持 640×480）
$P gr2boot.py repack --png bootimg/dvf_TDSt.png
$P gr2boot.py frm --img b01firm6_custom.bin --out rg2_v003_custom.frm
```

### 已验证的无损性

| 检查 | 结果 |
|---|---|
| PNG → brp → 镜像 往返 | **逐字节完全一致** |
| 原镜像 → frm 往返 | **逐字节完全一致，sha256 与官方原固件相同** |
| 替换样例回灌 | 仅 340,474 字节变化（占 frm 2.43%），其余零改动 |

往返 sha256 一致意味着：解码 → 编辑 → 编码 → 封装**整条链路无损**，
你做出的画面改动是唯一变量。

## 三、操作步骤

### 路径 A：刷自定义固件（改动固件本体）

```bash
# 1. 解出开机画面
$P gr2boot.py extract

# 2. 用任意图像编辑器编辑 bootimg/dvf_TDSt.png
#    要求：640×480，24 位 RGB
#    建议：先从原图出发改，保留 GR 原有的留白与文字位置，观感最协调

# 3. 回灌并打包
$P gr2boot.py repack --png bootimg/dvf_TDSt.png
$P gr2boot.py frm --img b01firm6_custom.bin --out rg2_v003_custom.frm
```

### 路径 B：用 TTL 脚本直接覆盖（更稳，推荐先试这个）

固件里已有 `A:/update.ttl` 这套脚本机制，且 `update.ttl` 的执行发生在 `fsys stop` 之前的
**可写状态**下，说明脚本具备改写内部文件系统的能力。若路径 B 可行，
它是**改动最小、最容易回滚**的方式——不碰固件容器，出问题只需把原 `.brp` 拷回去。

> ⚠ 本项目**未定位到用户在机内触发任意 TTL 脚本的入口**
> （见报告第 8 章：GR II 走的是产线控制台 / 调试 shell 通道，触发条件未知）。
> 因此路径 B 目前**只有理论可行性，缺实机验证**。
> 路径 A 虽是纯文件层操作、无需相机配合，但**存在未解决的校验和风险**（见第〇节），
> 失败后果也比路径 B 严重得多。**两者都不是「安全选项」，风险性质不同。**

## 四、风险与边界

| 风险 | 说明 | 缓解 |
|---|---|---|
| **刷砖** | ⚠ **路径 A 的首要风险**。开机画面改动落在 `nUpdateCsum` 校验范围内，
而工具链**未重算该校验和**，相机可能直接拒绝启动 | **补齐校验和重算之前，不要刷入自定义固件**；先确认「刷回原固件」可行 |
| **画面异常** | 色偏 / 花屏 / 尺寸不符 | 严格 640×480、RGB565 大端；先用样例图验证链路 |
| **外层容器校验** | 本工具未重建外层头部的总长度/校验字段 | 等长替换使其余字段保持原值，但**不等于校验和正确**（见第〇节） |
| **合规标识** | 改 `dvf_mark.brp` 触碰 FCC/CE/IC 认证标签 | 建议只改 `dvf_TDSt.brp` |

**必须说明的局限**：全部结论来自**静态分析 + 离线文件操作**，**相机侧零验证**。
我无法确认刷入后相机是否接受。在实机测试前，这份产物应视为**待验证的方案**。

## 五、下一步建议

1. **先补校验和**（最高优先级）：定位 `nUpdateCsum` 在 `.frm` 中的偏移与算法，
   用「改单字节探针法」反推。这是路径 A 的**唯一硬阻塞**。
2. **确认回滚能力**：用**未经修改的原版** `rg2_v003.frm` 走一遍刷写流程，
   确认相机能正常接受并启动。回滚能力未验证前，不要刷任何自定义固件。
3. **再考虑路径 B**：破解机内触发入口（第 8 章的作业调度表与调试 shell 通道），
   一旦能触发 TTL 脚本，覆盖单个 `.brp` 比刷整包固件安全得多。
4. 只改 `dvf_TDSt.brp`，不要动认证标签。
